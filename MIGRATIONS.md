## 1. Principle

Database structure changes must be delivered through version-controlled
migrations.

Never edit production schema manually except during a documented
emergency procedure.

### Implemented foundation

`packages/database/prisma/migrations/20260924000100_identity_foundation/migration.sql`
implements user/language enums, users, patient_profiles and sessions only, with
identity normalization/uniqueness, session checks and restrictive foreign keys.
The migration is transactional. PostgreSQL 17 supplies gen_random_uuid without
an extension. The subsequent `20260924000200_auth_audit` migration adds audit_logs
and its indexes. Other clinical/catalog/sharing tables remain future work.
Local runtime grants are applied separately with `pnpm db:grant-local`; portable
schema migrations do not embed environment-specific role names.
See [docs/API-DATABASE-FOUNDATION.md](docs/API-DATABASE-FOUNDATION.md) for local
migration commands and isolated database tests.

## 3. Migration rules

Every migration must:

-   have a unique version
-   have a descriptive name
-   be committed to source control
-   be tested against a clean database
-   be tested against representative existing data before production
-   avoid destructive operations without explicit approval

## 4. Production safety

For large tables:

-   avoid long blocking migrations
-   prefer additive changes first
-   backfill separately when needed
-   add indexes concurrently when appropriate
-   deploy application compatibility before removing old columns

## 5. Seed data

Seeds are separate from migrations.

Examples:

``` text
development seed
test seed
demo seed
```

Do not put the entire medicine catalog into the normal schema migration
chain.

## 6. Medicine imports

External medicine imports must use:

``` text
raw
 ↓
staging
 ↓
validation
 ↓
review
 ↓
publish
```

Never import directly into the production master catalog without
validation.

## 7. Rollback

A rollback must be evaluated for data safety.

For destructive changes, a forward corrective migration may be safer
than a rollback.

## 8. Migration acceptance test

A clean environment must support:

``` text
empty PostgreSQL
 ↓
run all migrations
 ↓
database ready
 ↓
run seed
 ↓
API starts
 ↓
tests pass
```

## Implemented catalog migration

`20260924000300_medicine_catalog` adds six catalog tables, their canonical enums,
foreign keys and indexes. Catalog relationships use RESTRICT deletion. SQL checks
reject empty names, unnormalized barcode text, negative image sort order and
non-HTTPS image URLs. This is additive; no identity/session data is rewritten.
Local runtime grants add SELECT only. Run the explicit `pnpm db:seed-catalog`
after migration/build to insert labeled synthetic development fixtures, never
real medical data. See [docs/MEDICINE-CATALOG.md](docs/MEDICINE-CATALOG.md).

## Implemented patient inventory migration

`20260924000400_patient_inventory` adds medication_inventory, inventory_unit and
inventory_source with RESTRICT foreign keys, numeric/date constraints and scoped
indexes. The unarchived-patient partial index is maintained in SQL. Local grants
allow only required INSERT/UPDATE columns and no DELETE. No existing catalog or
patient records are rewritten, and archive preserves quantities and references.
See [docs/PATIENT-INVENTORY.md](docs/PATIENT-INVENTORY.md).

## Implemented prescription draft migration

`20260924000500_prescription_drafts` adds prescription headers, medication summaries,
append-only field revisions and private document metadata with canonical enums.
RESTRICT relationships preserve history; document ownership is enforced by a
composite parent/patient foreign key. Revision uniqueness, actor/time consistency,
positive-or-null values, confidence and date bounds are enforced. Runtime field
revisions cannot be updated/deleted. D018 subsequently adds document INSERT and
private storage-key/retention SELECT to local runtime grants for owner uploads
and downloads. Document UPDATE/DELETE remain prohibited; no additional schema
migration is needed. See docs/PRESCRIPTION-DOCUMENTS.md.

## Implemented notification preference migration

`20260925000100_notification_preferences` adds optional per-user preferences with
required explicit booleans, nullable nonnegative INTEGER lead time, timestamps
and a RESTRICT user foreign key. It does not backfill users or choose defaults.
Runtime grants forbid deletion, ownership reassignment and created_at changes.

## Implemented treatment migration

`20260925000200_treatments` adds treatments, treatment_medications,
medication_schedules, medication_occurrences and medication_events. Required end
dates bound this first implementation; activated_at records explicit activation.
RESTRICT references, a composite prescription ownership FK, occurrence/event
uniqueness, date/dose checks and scope-validation triggers preserve history.
Runtime grants prohibit schedule/occurrence/event UPDATE and DELETE.

## Reminder inbox migration

`20260925000300_reminder_inbox` is the eighth implemented migration. It adds
notifications, durable occurrence deduplication, recipient foreign keys and the
DOSE_DUE-only constraint. Reapply `pnpm db:grant-local` after migration for the
restricted local API/worker principal. No existing occurrence is backfilled.
